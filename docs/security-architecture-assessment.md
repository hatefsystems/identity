## Architecture and Release Consequences

The central conflict is **where earned authority is stored and revalidated**, not
the absence of cryptography. Primary SQL must own authentication/preauth facts,
session deadlines/revocation, code-family generations, TOTP replay, contact
provenance and repair barriers. A coherent privileged SQL rewrite or stale restore
is still a threat after that redesign; SQL authority is not SQL-compromise immunity.
Use the [proposed persisted model](data-architecture.md#planned-security-authority)
and [STRIDE matrix](threat-modeling.md#authoritative-stride-matrix).

Do not enable phone-only production eligibility or retire T27 on documentation
alone. Notifications/readers precede security-changing writers, complete deletion
and retained reclaim factors precede gate retirement, and durable token/consumer/
restore prerequisites precede final T42 release. One code plus new-device UV is
not a surrogate for independent old ownership; time or regeneration cannot clear
the one-repair barrier. A repaired password may clear it only at SQL-recorded fresh
normal login satisfying that ordinary account's entire current policy.

## Unresolved Evidence

- No observed deployment inventory, exposed-Redis access path, selected-provider receipt, HA/failover durability or restore rollback witness was established.
- Verified privileged hardware provenance, independent backup and downstream assurance/freshness enforcement remain implementation and physical acceptance prerequisites.
- Multi-factor loss without surviving evidence remains deliberately blocked; no support override or privileged consumer-recovery procedure is invented.
- Current untyped saved artifacts require concrete dependency inventory and owner-approved handling before family separation; do not reinterpret them as both code purposes or delete stored history.
- Standards applicability and issuance conflicts require explicit policy mapping, not AAL/FAL/ASVS labels. Professional Persian security/legal review, approved legal/data rights, physical hardware and deployed ingress stay independent gates.
- Only documentation validation belongs to this delivery. The integrating parent records combined path/anchor/format/Mermaid checks in readiness/alignment; no application task is completed by this assessment.
