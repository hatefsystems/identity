## Owner-Confirmed Target Decisions

1. **Identification:** mandatory immutable username; intentional email identification requires the current verified uniquely associated primary email. Email and mobile are individually optional, but every production human account requires at least one verified contact. No implicit identifier fallback, hypothetical username-less lane, mobile identification, fabricated mailbox or empty-email digest. Discoverable passkey login remains available; named flows must not expose credential inventories.
2. **Normal authentication:** require an eligible password or passkey. Email/SMS alone never issue normal authority. Every passkey authentication requires actual server-verified UV, including trusted UV establishment; UP, authenticator availability, enrollment inventory, and new-device UV are not old-factor ownership.
3. **Independent MFA:** enabled/required independent MFA remains mandatory after UV. Allow TOTP or a policy-admitted MFA Backup Code; record primary method, actual UV, actual TOTP, backup consumption, and original authentication time separately. No normal session before complete policy validation.
4. **Privileged/high-assurance accounts:** administrators/privileged operators require policy-verified hardware-backed phishing-resistant UV authenticators and a separately enrolled independent backup. UV/AAGUID/transport/backup flags alone do not prove hardware backing. Privileged and higher-assurance accounts admit no consumer ARC+contact recovery, backup-code downgrade, support override, or administrative bypass. Total loss stays blocked until a separately approved higher-assurance procedure exists; do not invent that procedure or unapproved future assurance categories here.
5. **Two code families:** MFA Backup Codes complete primary-bound MFA; Account Recovery Codes (ARCs) plus fresh old-current verified email/mobile proof authorize one factor repair. Neither family automatically authorizes the other. Never deliver ARCs through email/SMS; use an explicitly authorized transient viewer/download and encourage independently protected offline storage.
6. **Ordinary recovery:** one ARC plus fresh ownership proof of an eligible existing verified destination; TOTP replacement additionally requires an eligible pre-existing primary. No normal/OAuth/admin/legal/contact/deletion/general-Step-up authority, automatic fallback, or recovery-code-only credential mutation. New passkey binding requires UV; old TOTP remains active until verified atomic replacement.
7. **Durable anti-chaining barrier:** after one successful factor repair, prohibit further recovery or equivalent factor-changing bypass until fresh normal authentication satisfies the complete authoritative policy. A newly repaired primary cannot immediately count as independent surviving evidence for another repair. Enforce through sessions, replicas, restarts, new challenges, code regeneration, credential/MFA management, and alternate endpoints. Time, contact OTP, refresh, and ARC possession cannot clear it. Multi-factor loss without sufficient pre-existing evidence/eligible backup is deliberately fail-closed. The owner clarified reset semantics: SQL-recorded fresh login with a repaired password may clear the barrier for an ordinary password-only account because it satisfies that account's entire policy; where independent MFA is required, the same password yields only preauthentication and cannot clear the barrier without actual required TOTP or a policy-eligible MFA Backup Code. Preserve required policy against management-endpoint downgrades during repair.
8. **Contact cooldown:** newly added/replaced verified contacts have a mandatory 24-hour recovery cooldown using server-recorded provenance and absolute UTC. Initial registration verification is exempt; unchanged eligible contacts may remain available. Unknown provenance is not assumed eligible. Reverification, removal/re-addition, browser changes, restart, and locale/time-zone changes cannot reset/bypass the restriction. Protect the last recovery-eligible destination and fence in-flight authority on relevant changes.
9. **PostgreSQL authority:** primary PostgreSQL governs earned evidence, normal/preauthentication authority, session issuance/deadlines/revocation, proof consumption, TOTP replay, account policy/security versions, credentials, and repair barriers. Extend existing services/contracts; Redis is non-authoritative acceleration/coordination/rate limiting only. Redis corruption/loss must neither grant authority nor silently disable critical abuse limits. No SQL+Redis atomicity claim.
10. **Durability/failure behavior:** account mutations and applicable consumption/security-version/barrier/audit-notification intent share one deciding SQL transaction with final policy checks. Use a documented global lock order; hash/native/provider work stays outside long-held locks. Unknown SQL/provider results do not authorize retries, new sessions, restored proofs, or recreated accounts. Read-only reconciliation reports facts, never reissues earned authority.
11. **Complete lifecycle:** preserve 30-day deletion grace, legal holds, username ownership, retained required reclaim factors, exact deadlines, and existing stronger deletion authorization. Password/mobile-only activation and T27 gate retirement remain blocked until independently verified recovery, notification, deletion, and reclaim capabilities exist.

Document proposed implementation choices explicitly: at least 128 random bits per saved code; new code families use purpose/account/generation-bound HMAC-SHA-256 with a dedicated key held separately from the database and distinct family domains. This is a stronger Hatef choice, not a claim that the existing high-entropy SHA-256 verifier is inherently insecure or that NIST universally mandates HMAC. No Argon2 treatment of high-entropy codes; constant-time application comparisons where applicable, without claiming constant-time SQL lookup. Saved codes remain usable until single use, family regeneration/revocation, deletion or policy ineligibility; this is distinct from grants and the transient viewer. Unspent ARC artifacts cannot earn a second repair while the barrier is set. Any replacement batch requires its own fresh issuance authority, never a recovery grant or automatic contact delivery. Preserve existing stricter budgets; propose one ten-minute absolute recovery ceremony and a repair grant capped at five minutes and the remaining original ceremony deadline, never another fresh ten minutes per stage. Define code-family generations and exact revocation triggers for ordinary changes, TOTP replacement, role changes, deletion, regeneration, and confirmed compromise; preserve unrelated uncompromised credentials and never reset the repair barrier by regeneration. Do not transparently reinterpret one existing untyped code as both purposes or delete real stored artifacts; inventory concrete dependencies and require owner-approved handling.

## Dependency and Release Ordering

Use a DAG, not numerical ordering:

```text
SQL security authority + evidence/policy + durable replay/admission
  -> privileged/identifier/actionproof/contact remediations
  -> code-family lifecycle -> MFA backup completion OR restricted recovery
  -> individual repairs + durable anti-chaining + fresh ordinary authentication

Security-event contract -> verified-destination notification/readers
  -> password/mobile deletion + reclaim
  -> T27 gate retirement and phone-only production eligibility

Validated personal/username/geography/legal prerequisites
  -> one registration service -> atomic birth -> fresh session
  -> registration/account UI integration

Durable token/IdP/consumer/restore prerequisites + all eligible lifecycles
  -> final independent T42 security and launch gates
```

Break notification/event/recovery cycles by defining contracts/readers and notification infrastructure **before** enabling security-changing writers; later tasks add their exact transactional intents and integration tests. T40 private snapshot work is independent of the early security-event foundation. Foundation/code/recovery code work and notifications may run in parallel only after authority/evidence contracts are agreed; UI work consumes fixed contracts rather than inventing them. Future integrating agent owns final combined verification.

Security review checkpoints: policy/ADR approval; SQL ownership/lock/rollback design; MFA/privileged/recovery admission; anti-chaining and contact cooldown; complete password/mobile lifecycle; registration/session/consumer authority; independent launch review. No prerequisite is considered complete because its documentation exists.
